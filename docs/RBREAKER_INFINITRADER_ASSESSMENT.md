2026-10-26后续：用户已授权实施独立模拟适配，并确认柜台风险度90%与原策略限制同时生效；最新允许按回测来源估计费率/保证金，以柜台实际风险度、资金和累计费用核对。实现及部署说明见[模拟盘适配](RBREAKER_INFINITRADER_SIMULATION.md)。下文保留实施前评估，不代表已经完成实际柜台验收。

评估日期：2026-10-26。范围为当前节点的代码与无限易PythonGO官方公开接口核对。尚未检查用户本机无限易版本、连接模拟柜台、发送订单或验证柜台费用。本次不是适配器实现或模拟盘验收，不改变回测框架、策略、结果与封存。

## 结论

具备移植可行性。信号、冻结风险预算和对锁业务逻辑可以保留；现有回调不能直接作为PythonGO策略运行，需要行情/日历适配、异步订单执行、账户同步与持久化恢复。工作量主要在交易状态管理，而非R-Breaker六价位计算。

评估对象为`configs/rbreaker.current_checkpoint.json`指向的历史手续费＋ATR20×1／当前权益1%风险定仓＋对锁节点。节点PnL19898846.32130元、夏普0.969945；2026-10-22统一回测重跑核心CSV相同。这些是历史回测证据，不是模拟盘或未来实盘收益承诺。

PythonGO当前官方文档提供Python策略、行情与成交回调以及交易接口，安装指引使用Python3.12，语言版本与本项目要求能够对齐。接口版本仍须以用户实际客户端为准，不能混用旧CtaTemplate/camelCase示例与新版BaseStrategy/snake_case接口。[官方入口](https://infinitrader.quantdo.com.cn/pythongo_v2/)、[安装环境](https://infinitrader.quantdo.com.cn/pythongo_v2/python_install)、[版本迁移](https://infinitrader.quantdo.com.cn/pythongo_v2/v1_to_v2)。

## 当前回调实际包含的部分

| 部分 | 当前代码 | 移植判断 |
|---|---|---|
| 六价位、突破/反转、当日高低、14:59隔夜判断 | `backtest/rbreaker.py`的`levels`、`RBreaker` | 可复用计算与规则，转换行情对象与时钟 |
| 主力选择 | `select_main`，运行器逐日调用 | 保留昨持仓量最大、成交量/代码打破平局；需新增实时日准备 |
| 组合资金分配、冻结目标、先退旧方向再反转 | `PortfolioRBreaker` | 可复用规则，账户权益与真实成交由平台接入 |
| ATR及交易级风险 | `TradeStops` | 保留简单20日TR均值、冻结风险及原始成交成本；需恢复跨日状态 |
| 解锁、新开、保护性对锁、旧主力库存清理 | `FeeAvoidingRBreaker` | 业务原则可移植；订单归属与撤改单状态机需要适配 |
| 实际成交价处资金复核 | `execution_guard` | 不能原样移植；报单前只能根据已知盘口与限价作预算，成交后再核对 |

`FeeAvoidingRBreaker.__call__`读取time、bars、auctions、marks、account.equity、positions以及fills_since，输出target_group。它不直接修改Ledger，存在可替换的上下文边界，但begin_day、历史ATR输入、09:25/09:30事件和日终调度目前由离线运行器负责，并非回调本身已包含的实时能力。

## 必须补齐的业务细节

### 1. 先保留分钟信号语义

当前节点用完整分钟OHLC判断信号和ATR触价，最早随后允许时点交易。迁移初版应保持这一规则。on_tick更新行情，on_trade更新成交事实，并不意味着每个Tick重新运行开仓信号。

如果将止损改为Tick触价立即执行，或者直接用未完成K线产生突破/反转，会改变策略，应另作试验。不能为了实时化就把止损机制悄悄改掉。

PythonGO的K线工具分别提供完成K线和实时更新入口；历史K线也可能进入相同回调。历史预热期间必须关闭报单，只构建指标与可验证状态，不能补发历史信号。启动在盘中时还须补齐当日已完成分钟和当日高低，避免从启动时重新计算。[K线工具](https://infinitrader.quantdo.com.cn/pythongo_v2/modules/pythongo_utils)、[官方第二个策略示例](https://infinitrader.quantdo.com.cn/pythongo_v2/tutorial/second_strategy)。

ATR必须使用同一实际合约此前20交易日的简单TR均值，TR按前一日收盘而非结算价计算，不直接替换为平台默认ATR或主连复权ATR。昨日H/L/C、昨日持仓量和成交量需要在开盘前准备好；不能以盘中实时主力变化替换原昨持仓量规则。

### 2. 集合竞价与日终不能只依赖收到下一条Tick

09:30在原回测中是独立竞价结果。旧主力清理在09:25逻辑时钟预提交；新信号看到09:30结果后只能参与后续连续交易。模拟盘须按实际合约状态确认可报单窗口、有效订单和成交回报，不能把回测09:25事件当成柜台已接受订单的证据。

竞价开盘价可来自平台行情，但不能只凭第一个Tick的时钟认定它包含完整竞价事件。需实录核对竞价成交、累计成交量及第一根连续分钟，避免把竞价重复计入分钟或漏掉开盘高低。

14:59完成分钟后的隔夜判断，以及午休/收盘边界，需有交易时段感知的定时协调和缺行情处理。不能等到15:00完整行情才用其信息决定14:59订单，也不能因未到下一条Tick而漏执行。延迟时仅在当前真实可交易时点报单，不能回填。

### 3. 对锁规则必须按账户级真实成交维护

所有平仓含解锁，先检查同账户、同实际合约、同持仓方向、同交易日的当日未消耗开仓计费余额；余额非零改反向开仓。当前主力锁仓等信号，旧主力先清理，未完成阻止同品种新主力入场。解锁与新开共用同一冻结目标，不能重复定仓。

该余额不能仅用当前“今仓”或净持仓猜测。需要完整成交流、平台开平语义及柜台计费匹配核对。若人工或其他策略也交易相同合约，必须计入账户级余额，并额外区分本策略可操作的库存归属。初期采用独立模拟账户更便于核验；若不能取得足够完整的账户成交信息，则不能宣称保持零平今。

PythonGO文档把`auto_close_position`说明为平今优先，故不能绕过本策略路由直接调用它。应使用明确开平意图的下单路径；具体中金所编码与柜台收费需现场核对。[官方交易接口](https://infinitrader.quantdo.com.cn/pythongo_v2/modules/pythongo_base)。

即使模拟柜台统一按低费率收费，也应独立核对是否产生按当前计费规则应算平今的平仓数量。显示低费用不是避免平今已经验收。

### 4. target_group要改为真实目标订单管理

当前`Engine._reconcile_target`在内存中立即取消旧待执行操作；真实撤单则可能等待确认、失败，或期间继续成交。必须将目标、已成交、在途未成交和撤单中数量分开；撤单发送成功不能直接当撤单完成，也不能提前释放资金和可平量。

当前`self.route[(group,effect)]`是可更新映射，在离线引擎时序下可用。移植后每笔订单需要冻结action、logical_side、风险交易ID、目标版本及开平意图，并通过order_id/交易所报单标识关联。晚到成交不能误用新目标的route解释。成交去重键需结合交易日/账户/交易所等实际字段，不能假设order_id或trade_id跨重启全局唯一。

原`execution_guard`可查询候选成交的准确费用与价格；报单前无法知道实际成交。因此适配器只能使用已知报价/限价、当前规则与预留预算作报单前检查，并在每笔真实成交后重算。跳价、费用变化和拒单风险仍存在，不能复制回测的成交前精确复核保证。[回报与撤单语义](https://infinitrader.quantdo.com.cn/pythongo_v2/modules/pythongo_base)、[订单字段](https://infinitrader.quantdo.com.cn/pythongo_v2/modules/pythongo_classdef/order)。

### 5. 真实资金与成交条件不能沿用模拟数值保证

保留净敞口50%、真实大边总90%的策略准入原则，同时按柜台实际保证金、冻结金额、可用资金和费用核验。15%只保留为研究对照参数，不能作为实际柜台保证金或可成交资金的替代。账户数据可能晚于最新成交，需记录快照时间并预留尚未反映的订单/成交，避免重扣已反映的冻结。官方资金说明区分柜台查询与客户端计算，以实际柜台与结算单为准。[官方资金说明](https://infinitrader.quantdo.com.cn/docs/quick_start/b4_fund.html)。

10%参与率使用的是分钟撮合模型的成交量约束，真实报单时不知道随后一分钟的最终成交量；实际执行需要显式选择基于已发生量动态限制或其他可执行方法，并单列与回测的差异。连续不利1tick不是实际成交价格保证；限价、盘口、排队及撤补单策略需明确，不能把虚拟滑点再次加到实际成交账务。

当前回测所有阶段观测资金峰值94.57691%，不能据此断言真实柜台一定接受保护性对锁。若反向开仓因资金不足被拒，净敞口仍未退出。按当前节点只能保留退出意图、重试和报告；不能记成已止损，也不能自动改直接平今。若未来实盘需要“资金不足时允许付平今费优先退出”等降级策略，须单独确认和测试，本次不引入。

### 6. 重启恢复与每日结算

至少保存：物理订单映射、真实成交日志/去重索引、逻辑方向库存、入场模式、冻结ATR/风险预算/目标数量、原始入场成本、止损/冷却状态、当日计费余额、旧主力清理进度、未完成指令。参数或净持仓快照不足以重建这些状态。

启动先查询账户/持仓/活动订单并回放可获取的真实成交，与本地持久化日志对账；未对齐时停止新增方向，保留可识别的退出意图并报告。不能将重启时的锁仓当成新信号入场，也不能因重启清空当日计费余额。成交日志需要逐事件可靠落盘，不能只依赖用户主动暂停才保存实例。

每日结算以柜台/结算单为资金事实，核对手续费、保证金、双边库存和权益；跨日重置当日计费余额应按交易日推进，冻结ATR和交易原始入场成本继续保留。可以保留独立审计重放，但不得把审计计算再次写入真实账户或与柜台盈亏重复相加。

## 最小移植结构与验证顺序

建议在回测框架外建立平台适配层：

```text
无限易行情/订单/成交/账户
        ↓
行情时钟与账户适配 + 可靠事件日志
        ↓
同一份R-Breaker信号、风险目标与对锁原则
        ↓
目标订单管理 + 报单前预算核对
        ↓
PythonGO报单、撤单与实际回报
```

第一版用一个组合实例协调四品种、一个指定模拟账户，避免四个互不知情的实例分别占用同一份资金。不在真实交易路径运行回测Engine生成虚拟Fill，不另建权威现金账本。当前源码会传递引入离线数据相关模块，可在适配阶段整理导入边界；不得因此改动封存源码。

1. **离线等价验证。** 固定行情、账户观察和保存真实成交，平台无关部分应与节点产生一致信号、目标、ATR预算、冷却和路由。严格比对依赖相同输入，不要求真实模拟成交后仍逐笔复现原回测仓位。
2. **实时报价观察。** 不下单，记录分钟/竞价、主力、指标及信号；确认分钟边界、历史预热、四品种同步、午休与14:59处理。
3. **模拟交易闭环。** 验证普通新开、保护性对锁、次日解锁、旧主力双边清理；全部以真实成交推动状态，按结算单核对PnL和费用。
4. **故障与边界。** 部分成交、重复/迟到回报、撤单期间成交、拒单、断线重连、盘中重启、跨日计费、同时多品种请求、资金不足无法开锁。不能只看正常行情跑了几天。

验收指标为：信号口径一致；无重复订单/成交记账；所有实际成交可关联订单与路由；未完成退出不假报完成；实际双向库存和净方向一致；按已确认计费规则平今数量为零；每日权益/费用/保证金可对账；资金超限与拒单完整保留。若柜台按本策略假设以外方式计费或不支持所需对锁占用，则先定位差异，不宣称迁移通过。

本机客户端及PythonGO具体版本、模拟站点、股指期货权限、双向开仓能力、实际保证金/费率、账户成交与活动订单恢复能力，均属下一阶段待核对项。公开文档确认“存在接口”与本账户“已可用”是两回事。
